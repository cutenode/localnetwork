# Flags turn off and preview without touching their targeting

A flag in a rollout that turns out to have a bug needs to go off for everyone at once, and back on later for the same people. So `computer.localnetwork.staff.flag` has an `enabled` boolean that sits in front of the targeting: when it's false the flag is off for everyone, and its groups, accounts and percentage stay stored. It's optional, and missing means true, so records written before it and readers that don't know it behave as they did. `getFlags` sends `enabled` alongside each flag's stored gates instead of hiding a disabled flag's gates, so locallibrary decides from the same inputs as the website, and the `enabled` cases in `flags/vectors.json` hold both to one rule. Turning a flag off or on is a `flag.update` in the audit log, like any other change to it.

There are two ways to see a flag without changing who it's on for. `FLAG_OVERRIDES` is read at startup, for development and tests, and applies to every request on that instance, `getFlags` included. The website refuses to start if it's set with `NODE_ENV=production`, since there it would change the site for everyone with nothing in the staff console to show it, or if it names a flag the catalog doesn't have, since a typo would otherwise do nothing quietly. Staff use a preview instead: a cookie, set from the flag's page in the staff console, that turns one flag on or off for their own browser for an hour. Each instance keeps its own SQLite and syncs every 60 s, so a preview stored on the server would hold only on the instance that wrote it until the next sync, and the browser's requests land on any instance; a cookie goes with the browser. It's signed with the browser's session token, so there's no other secret to manage, and it stops working when they sign out or another account signs in. It's honoured only while the viewer holds the `flags` grant, so losing the grant ends it early, and every preview and clear is audited as `flag.preview`, like everything else staff do in the console. `getFlags` ignores it.

## Considered options

- Clearing every gate to turn a flag off, as the form did at first: no new field, but the record no longer says who the flag was for, and the audit log is the only place to rebuild it from.
- A required `enabled`: every existing record and every reader that doesn't know the field would need changing at once.
- Answering a disabled flag in `getFlags` as off for everyone at 0%: locallibrary would need nothing new, but the website would be applying part of the rule for it, and the vectors couldn't check that locallibrary applies `enabled` the same way.
- Previews in a server-side table: survives a cookie being cleared, but doesn't follow the browser across instances until the next sync, and needs its own expiry.
- A preview cookie signed with its own secret: one more secret per deployment to set and rotate, and the preview would outlive signing out.
