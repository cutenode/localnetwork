# Feature flag platforms compared with Local Network's flags

Local Network already has the part of feature flagging that every platform agrees on, and most of what it lacks isn't worth building at this size. The website has boolean flags declared as checked-in JSON files, targeting stored as private AT Protocol records, a salted SHA-256 percentage rollout, named groups, server-side evaluation from an in-memory snapshot, per-viewer booleans delivered with each page, grant-based permissions and a hash-chained audit log. LaunchDarkly, Statsig, Harness FME, ConfigCat, PostHog, Unleash, Flagsmith, GrowthBook, Flipt, GO Feature Flag and flagd all build on the same core. The locallibrary half asks the website for flags, keeps the answer for an hour and falls back to it for up to 14 days offline. [ADR 0006](../adr/0006-locallibrary-asks-the-website-for-flags.md) describes it, but the client isn't merged yet. Next to the platforms, Local Network is ahead on audit and on catching removed flags at compile time, level on hashing and delivery, and was behind on flag hygiene and day-to-day operations. Five gaps were worth closing before the first real feature goes behind a flag, and they are closed: `flags/**` is in CI's path filters, a flag can be turned off without losing its targeting, flags can be overridden in development and previewed by staff, the catalog records each flag's type and removal date, and the staff console says when a flag is ready to remove. Multivariate values, attribute rules, environments as objects, approvals, scheduled or guarded rollouts, streaming, experiments and OpenFeature are what the paid tiers sell, and none of them pays off at this scale.

Links into this repo are pinned to [`2f9d6c9`](https://github.com/cutenode/localnetwork/tree/2f9d6c93a3b8dbb68fae3b9806ab85af26398ea5), where the website flags had landed in [PR #456](https://github.com/cutenode/localnetwork/pull/456) with an e2e fix in [PR #516](https://github.com/cutenode/localnetwork/pull/516). "On main" means that commit plus the change that added this document, which brought the CI path filter, the kill switch, the overrides, the catalog's type and removal date, and the "Ready to remove" marker. The pinned links show the code from before that change. [ADR 0010](../adr/0010-flags-turn-off-and-preview-without-touching-targeting.md) records why the kill switch and the overrides work the way they do.

## How each feature area compares

Every platform in the set evaluates a flag the same way: it checks for a kill or off state, runs through targeting (named individuals first, then rules or segments), falls back to a hashed percentage split, and returns a default when nothing matches. They differ in how much of that ships to clients, how fast changes arrive, and how much governance sits around it.

## Flag model and targeting

A flag is two separate things. Its existence is a file in `flags/catalog/`. At `2f9d6c9` that file had exactly two fields, a camelCase `key` and a `description`, and the schema forbade anything else ([flag.schema.json](https://github.com/cutenode/localnetwork/blob/2f9d6c93a3b8dbb68fae3b9806ab85af26398ea5/flags/flag.schema.json#L9-L26)); it now also has a `type` and, for some types, a `removeBy` date, covered under [hygiene](#hygiene-and-removal). The README sums up the lifecycle: "To add a flag, add a file. To remove one, delete its file, and the website stops compiling wherever it's still used" ([flags/README.md](https://github.com/cutenode/localnetwork/blob/2f9d6c93a3b8dbb68fae3b9806ab85af26398ea5/flags/README.md#L3-L5)). A generated `FlagKey` union makes that true for the type checker ([flag-keys.ts](https://github.com/cutenode/localnetwork/blob/2f9d6c93a3b8dbb68fae3b9806ab85af26398ea5/apps/web/scripts/flag-keys.ts#L1-L19)). Its targeting lives somewhere else: a `computer.localnetwork.staff.flag` record in the root account's private staff space, with `everyone`, `percentage` (0 to 100), up to 100 `groups` and up to 1000 `dids`, where "Any gate that matches turns it on" ([staff/flag.json](https://github.com/cutenode/localnetwork/blob/2f9d6c93a3b8dbb68fae3b9806ab85af26398ea5/lexicons/computer/localnetwork/staff/flag.json#L6-L35)). The record now also has an optional `enabled`, described under [the kill switch](#the-kill-switch). Groups are their own TID-keyed records holding up to 5000 members, so renaming a group touches no flag ([staff/group.json](https://github.com/cutenode/localnetwork/blob/2f9d6c93a3b8dbb68fae3b9806ab85af26398ea5/lexicons/computer/localnetwork/staff/group.json#L6-L23)). The only flag in the catalog is `parityCanary`, which "Gates nothing" and exists to check that the website and locallibrary agree ([parityCanary.json](https://github.com/cutenode/localnetwork/blob/2f9d6c93a3b8dbb68fae3b9806ab85af26398ea5/flags/catalog/parityCanary.json#L4)).

Keeping the flag's definition in git and its runtime state elsewhere is what Martin Fowler's toggle article recommends: keep toggle config version-controlled where possible, with dynamic reconfiguration for the cases that need it ([Fowler](https://martinfowler.com/articles/feature-toggles.html)). Flipt v2 and GO Feature Flag go furthest the other way, keeping the whole flag, targeting included, in git or plain files ([Flipt intro](https://docs.flipt.io/v2/introduction); [GOFF relay proxy](https://gofeatureflag.org/docs/relay-proxy/configure-relay-proxy)). Local Network sits between them. Which keys exist is compiled in, while who gets what lives in records that can change without a deploy and rebuild from the network.

The commercial targeting model is richer. LaunchDarkly evaluates prerequisites, then individual targets, then ordered rules whose clauses are ANDed over typed context attributes with operators like `semVerGreaterThan`, `matches` and `segmentMatch`, then a fallthrough ([LD evaluation rules](https://launchdarkly.com/docs/sdk/concepts/flag-evaluation-rules)). Statsig offers conditions on app version, country, browser, IP, environment tier and custom fields ([Statsig conditions](https://docs.statsig.com/feature-flags/conditions)). ConfigCat, Flipt, GrowthBook and GO Feature Flag all use ranked rules where the first match wins ([ConfigCat targeting](https://configcat.com/docs/targeting/targeting-overview/); [Flipt concepts](https://docs.flipt.io/v2/concepts); [GrowthBook rules](https://docs.growthbook.io/features/rules); [GOFF internal_flag.go](https://github.com/thomaspoignant/go-feature-flag/blob/v1.58.1/modules/core/flag/internal_flag.go#L162-L190)). Local Network's "any gate turns it on" is the other common shape: Unleash ORs its strategies together ([Unleash activation strategies](https://docs.getunleash.io/concepts/activation-strategies)), and PostHog ORs its condition sets unless you opt into first-match ([PostHog creating flags](https://posthog.com/docs/feature-flags/creating-feature-flags)). With booleans only, rule order can't change an answer, so the OR model loses nothing.

The data-model gaps are real but cheap to skip. Multivariate values, JSON payloads and remote config matter when a flag chooses between several behaviors or tunes a parameter, and the glossary scopes flags to rollouts: "Flags are for rolling something out, not for keeping anyone out" ([GLOSSARY.md](https://github.com/cutenode/localnetwork/blob/2f9d6c93a3b8dbb68fae3b9806ab85af26398ea5/GLOSSARY.md#L23-L32)). Attribute rules and multi-entity contexts (LD's multi-contexts, FME's traffic types, PostHog's groups) answer questions like "turn this on for Android 14 users in Germany", which a DJ directory with a few hundred accounts doesn't ask. Prerequisites earn their keep in organizations with hundreds of interlinked flags, and GrowthBook and Unleash add cycle detection and delete protection to them for that reason ([GrowthBook prerequisites](https://docs.growthbook.io/features/prerequisites); [Unleash flags](https://docs.getunleash.io/reference/feature-toggles)). Local Network already has delete protection for groups: a group a flag uses can't be deleted, "so deleting one can't quietly turn a flag off for its members" ([services/flags.ts](https://github.com/cutenode/localnetwork/blob/2f9d6c93a3b8dbb68fae3b9806ab85af26398ea5/apps/web/src/lib/server/services/flags.ts#L282-L303)).

The size limits hold up as well. Harness FME caps individual targets at 500 IDs per flag and pushes anything larger into segments ([FME targeting](https://developer.harness.io/feature-management-experimentation/use-fme/feature-management/setup/define-feature-flag-treatments-and-targeting)), and Unleash advises against putting large user lists in flag configs at all ([Unleash best practices](https://docs.getunleash.io/topics/feature-flags/feature-flag-best-practices)). Local Network allows 1000 DIDs per flag and 5000 per group, with groups doing the job of segments.

One targeting gap rates low but is worth noting. Nothing in the model turns a flag off for one person. LaunchDarkly segments carry `excluded` lists ([LD evaluation rules](https://launchdarkly.com/docs/sdk/concepts/flag-evaluation-rules)) and Flagsmith rules support `NONE` ([flagsmith-engine constants](https://github.com/Flagsmith/flagsmith-engine/blob/v11.1.2/flag_engine/segments/constants.py)). If one account in a 30% rollout hits a bug, Local Network can lower the percentage or turn the flag off for everyone, but it can't take out just that account. Excluding someone is still a rollout operation and doesn't conflict with the glossary, but at current scale it's an edge case.

## Hashing and percentage rollouts

Local Network's rule fits on one line. At `2f9d6c9` it was `on = everyone || targeted || (did is known && bucket(key, did) < percentage)`, where the bucket is the first 4 bytes of `sha256(key + did)`, big-endian, mod 100 ([flags/README.md](https://github.com/cutenode/localnetwork/blob/2f9d6c93a3b8dbb68fae3b9806ab85af26398ea5/flags/README.md#L17-L24); [evaluate.ts](https://github.com/cutenode/localnetwork/blob/2f9d6c93a3b8dbb68fae3b9806ab85af26398ea5/apps/web/src/lib/server/flags/evaluate.ts#L7-L19)). The kill switch puts `enabled &&` in front of it. Every evaluator is held to the shared cases in [flags/vectors.json](https://github.com/cutenode/localnetwork/blob/2f9d6c93a3b8dbb68fae3b9806ab85af26398ea5/flags/vectors.json), 68 of them at that commit ([PR #456](https://github.com/cutenode/localnetwork/pull/456)), and ADR 0006 has locallibrary apply the same rule. This is how it compares with the platforms' own code.

| System          | Hash                      | Hashed input                                    | Resolution                                                                                                                                                                                  |

| LaunchDarkly    | SHA-1, first 15 hex chars | `flagKey.salt.value`                            | 100,000 buckets ([go evaluator](https://github.com/launchdarkly/go-server-sdk-evaluation/blob/v3/evaluator_bucketing.go); [LD rollouts](https://launchdarkly.com/docs/home/flags/rollouts)) |
| Statsig         | SHA-256, first 8 bytes    | `configSalt.ruleSalt.unitID`                    | 10,000 ([Evaluator.ts](https://github.com/statsig-io/node-js-server-sdk/blob/main/src/Evaluator.ts#L1159-L1176))                                                                            |

The properties that matter are all there. The flag key acts as a per-flag salt, so the same 10% of accounts don't land in every rollout, which flagd describes as keeping "assignments independent across flags" ([flagd fractional](https://flagd.dev/reference/custom-operations/fractional-operation/)) and which Local Network tests directly ([evaluate.test.ts](https://github.com/cutenode/localnetwork/blob/2f9d6c93a3b8dbb68fae3b9806ab85af26398ea5/apps/web/src/lib/server/flags/evaluate.test.ts#L55-L59)). The threshold only moves up, so raising a percentage only adds accounts. Every vendor documents that stickiness ([Statsig FAQ](https://docs.statsig.com/faq/); [Unleash stickiness](https://docs.getunleash.io/concepts/stickiness)), and Local Network covers it with fast-check property tests ([evaluate.test.ts](https://github.com/cutenode/localnetwork/blob/2f9d6c93a3b8dbb68fae3b9806ab85af26398ea5/apps/web/src/lib/server/flags/evaluate.test.ts#L1-L60)). The 100-bucket resolution matches Unleash, ConfigCat and FME. Reducing a 32-bit value mod 100 biases the buckets by about two parts in a hundred million, which doesn't matter.

Shared vectors guard against a failure the platforms have run into, where SDKs in different languages drift apart. flagd changed its hashing in v0.18.0 and now requires flagd and every provider to upgrade together ([flagd fractional](https://flagd.dev/reference/custom-operations/fractional-operation/)). GrowthBook had to ship a second hash version after v1 "had a flaw that caused bias when running experiments in parallel" and pins UTF-16 code units to keep SDKs consistent ([GrowthBook SDK spec](https://docs.growthbook.io/lib/build-your-own)). Flipt's own docs describe its hash input differently from what its v2.14.1 code does ([Flipt concepts](https://docs.flipt.io/v2/concepts) vs [evaluation.go](https://github.com/flipt-io/flipt/blob/v2.14.1/internal/server/evaluation/evaluation.go#L240-L280)). One vectors file that every evaluator must pass is the cheap version of OpenFeature's provider conformance kit.

Two hashing features are missing, and neither matters yet. LaunchDarkly, Statsig and Flagsmith keep a salt separate from the flag key, so a flag can be renamed without reshuffling anyone, and an operator can re-salt on purpose to reshuffle: "To reshuffle all users, you must resalt the gate" ([Statsig FAQ](https://docs.statsig.com/faq/); [LD salt support article](https://support.launchdarkly.com/hc/en-us/articles/36961986486811-How-to-update-the-flag-salt); [Flagsmith models.py](https://github.com/Flagsmith/flagsmith/blob/v2.290.0/api/features/models.py#L774-L781)). In Local Network, renaming a key means a new catalog file and a fresh rollout anyway, so a separate salt would buy nothing. The second is signed-out visitors. LaunchDarkly gives them a random key kept in local storage, PostHog buckets by `$device_id`, Unleash falls back to a random number with no stickiness, and Statsig buckets empty IDs on the salt alone, so every anonymous visitor gets the same answer ([LD anonymous contexts](https://launchdarkly.com/docs/home/flags/anonymous-contexts); [PostHog device bucketing](https://posthog.com/docs/feature-flags/device-bucketing); [Unleash stickiness](https://docs.getunleash.io/reference/stickiness); [Statsig evaluation](https://docs.statsig.com/sdks/how-evaluation-works)). Local Network leaves signed-out visitors out of percentages ([flags/README.md](https://github.com/cutenode/localnetwork/blob/2f9d6c93a3b8dbb68fae3b9806ab85af26398ea5/flags/README.md#L17-L24)), which avoids PostHog's documented problem of a user's bucket changing after sign-in ([PostHog creating flags](https://posthog.com/docs/feature-flags/creating-feature-flags)). That's the right default for a site where new features are aimed at signed-in DJs.

The time-based rollout tools are where the paid tiers live. LaunchDarkly's progressive rollouts ramp a percentage on a schedule, and its guarded rollouts watch metrics and roll back automatically on a significant regression, which needs Enterprise plus the Guardian add-on ([LD progressive](https://launchdarkly.com/docs/home/releases/progressive-rollouts); [LD guarded](https://launchdarkly.com/docs/home/releases/guarded-rollouts)). Statsig has release pipelines and rollout alerts ([Statsig release pipeline](https://docs.statsig.com/release-pipeline); [rollout alerts](https://docs.statsig.com/metrics/rollout-alerts)). PostHog schedules changes on cron ([PostHog scheduled changes](https://posthog.com/docs/feature-flags/scheduled-flag-changes)), and GO Feature Flag offers `scheduledRollout` and `progressiveRollout` for free ([GOFF internal_flag.go](https://github.com/thomaspoignant/go-feature-flag/blob/v1.58.1/modules/core/flag/internal_flag.go#L209-L262)). Guarded rollouts need a metrics pipeline Local Network doesn't have, and scheduled ramps save a few clicks spread over a week. Neither is worth building.

## Delivery, privacy and update speed

On delivery, Local Network matches the pattern the platforms converge on. LaunchDarkly server SDKs receive "the complete ruleset" and evaluate locally, while its client SDKs get only evaluated results ([LD client vs server](https://launchdarkly.com/docs/sdk/concepts/client-side-server-side)). Statsig server SDKs need no network request per check and take under 1 ms ([Statsig evaluation](https://docs.statsig.com/sdks/how-evaluation-works)), and Unleash frontends receive "only enabled flags and their variants" through its frontend API ([Unleash SDKs](https://docs.getunleash.io/sdks)). Local Network's `FlagService` holds one in-memory snapshot loaded from SQLite and drops it after every write or synced change, "so checking one on every request costs nothing" ([services/flags.ts](https://github.com/cutenode/localnetwork/blob/2f9d6c93a3b8dbb68fae3b9806ab85af26398ea5/apps/web/src/lib/server/services/flags.ts#L69-L89)). The server hook evaluates every catalog flag for the viewer on each non-XRPC request ([hooks.server.ts](https://github.com/cutenode/localnetwork/blob/2f9d6c93a3b8dbb68fae3b9806ab85af26398ea5/apps/web/src/hooks.server.ts#L103)), and the root layout hands the booleans to pages ([+layout.server.ts](https://github.com/cutenode/localnetwork/blob/2f9d6c93a3b8dbb68fae3b9806ab85af26398ea5/apps/web/src/routes/%2Blayout.server.ts#L5-L16)).

LaunchDarkly calls that root-layout handoff bootstrapping. Its client SDK needs it to avoid a page that "waits for the client to fetch flags" and flickers from defaults to real values ([LD bootstrapping](https://launchdarkly.com/docs/sdk/features/bootstrapping)), and PostHog sells the same thing ([PostHog bootstrapping](https://posthog.com/docs/feature-flags/bootstrapping)). Because SvelteKit renders on the server, Local Network gets it without a client SDK: a page never sees a flag before its real value. PR #456 also handled the cost. Layout data now varies by account, so the mix page moved from `public, max-age=300` to a helper that marks a response `private` whenever there's a viewer ([mix page](https://github.com/cutenode/localnetwork/blob/2f9d6c93a3b8dbb68fae3b9806ab85af26398ea5/apps/web/src/routes/projects/%5Bslug%5D/mixes/%5Bn%5D/%2Bpage.server.ts#L28-L29); [http.ts](https://github.com/cutenode/localnetwork/blob/2f9d6c93a3b8dbb68fae3b9806ab85af26398ea5/apps/web/src/lib/server/http.ts#L199-L206)). Flags aren't evaluated again after hydration, so a change shows up on the next navigation. Platforms stream to keep open tabs current, but LaunchDarkly's JS client only streams while a change listener is registered ([LD client vs server](https://launchdarkly.com/docs/sdk/concepts/client-side-server-side)), so even they rarely think it's needed.

Local Network gets privacy mostly right. Unleash's guidance is to evaluate server-side and never ship targeting rules to clients ([Unleash best practices](https://docs.getunleash.io/topics/feature-flags/feature-flag-best-practices)). ConfigCat breaks that by design, since its frontend SDKs expose the whole config JSON, rules included ([ConfigCat SDK README](https://npmjs.com/package/@configcat/sdk)). Local Network never sends group or DID lists anywhere, and the public `getFlags` endpoint says "Group names and member lists aren't exposed" ([getFlags.json](https://github.com/cutenode/localnetwork/blob/2f9d6c93a3b8dbb68fae3b9806ab85af26398ea5/lexicons/computer/localnetwork/flags/getFlags.json#L5-L38)). Two things do leak. Every catalog key and its boolean ride along in every page's layout data, which the e2e test confirms by reading `__data.json` ([app.e2e.ts](https://github.com/cutenode/localnetwork/blob/2f9d6c93a3b8dbb68fae3b9806ab85af26398ea5/apps/web/tests/e2e/app.e2e.ts#L548-L588)), and `getFlags` tells anyone each flag's `enabled`, `everyone` and `percentage`. LaunchDarkly filters with `client_side_only` ([LD bootstrapping](https://launchdarkly.com/docs/sdk/features/bootstrapping)) and Statsig hashes config names in client responses by default ([Statsig FAQ](https://docs.statsig.com/faq/)). For Local Network, this only matters if a flag's name would give away an unannounced feature, and neutral key names solve that without code.

Update speed and outage behavior are fine for a small site. Platforms push changes with SSE (LaunchDarkly, FME) or poll every 10 s (Statsig), 15 s (Unleash backend), 30 s (PostHog) or 60 s (ConfigCat) ([LD data saving mode](https://launchdarkly.com/docs/sdk/features/data-saving-mode); [FME SDKs](https://developer.harness.io/feature-management-experimentation/new-to-fme/sdks-and-customer-deployed-components); [Statsig server](https://docs.statsig.com/server/introduction); [Unleash SDKs](https://docs.getunleash.io/sdks); [PostHog local evaluation](https://posthog.com/docs/feature-flags/local-evaluation); [ConfigCat caching](https://configcat.com/docs/advanced/caching/)). In Local Network a change applies on the next request of the instance that wrote it. Any other instance picks it up when its sync loop runs, every `SYNC_POLL_INTERVAL_MS`, 60 s by default ([config.ts](https://github.com/cutenode/localnetwork/blob/2f9d6c93a3b8dbb68fae3b9806ab85af26398ea5/apps/web/src/lib/server/config.ts#L76); [app.ts](https://github.com/cutenode/localnetwork/blob/2f9d6c93a3b8dbb68fae3b9806ab85af26398ea5/apps/web/src/lib/server/app.ts#L509)). The public `getFlags` answer can be cached for 60 s ([get-flags.ts](https://github.com/cutenode/localnetwork/blob/2f9d6c93a3b8dbb68fae3b9806ab85af26398ea5/apps/web/src/lib/server/flags/get-flags.ts#L20-L59)). That's ConfigCat's default speed. Outages are covered too: evaluation reads local SQLite that rebuilds from the network, and an integration test wipes both flag tables and checks they come back ([flows.test.ts](https://github.com/cutenode/localnetwork/blob/2f9d6c93a3b8dbb68fae3b9806ab85af26398ea5/apps/web/tests/integration/flows.test.ts#L1089-L1121)). A failed load isn't cached, and a missing record means off, which is the "degrade gracefully" contract Unleash and OpenFeature both describe ([Unleash best practices](https://docs.getunleash.io/topics/feature-flags/feature-flag-best-practices); [OpenFeature spec 1.4.10](https://raw.githubusercontent.com/open-feature/spec/main/specification/sections/01-flag-evaluation.md)).

### The locallibrary client

ADR 0006 records the design: locallibrary can't read the private staff space, so it asks the website's `getFlags`, gets "every flag's public gates (on for everyone, and a percentage) and one private bit, `targeted`," hashes its own DID for the percentage, asks again when its answer is over an hour old, and "keeps the last answer for 14 days for computers that are offline" ([ADR 0006](https://github.com/cutenode/localnetwork/blob/2f9d6c93a3b8dbb68fae3b9806ab85af26398ea5/docs/adr/0006-locallibrary-asks-the-website-for-flags.md#L3-L5)). The kill switch adds `enabled` to those public gates. The website side is on main. `getFlags` answers anonymous callers publicly and verifies an AT Protocol service JWT (audience the app's did:web, `lxm` getFlags) before returning a `private, no-store` answer with `targeted` set for the caller ([get-flags.ts](https://github.com/cutenode/localnetwork/blob/2f9d6c93a3b8dbb68fae3b9806ab85af26398ea5/apps/web/src/lib/server/flags/get-flags.ts#L20-L59)). The hosted OAuth client document already allows the scope locallibrary will request ([oauth-client-metadata.json](https://github.com/cutenode/localnetwork/blob/2f9d6c93a3b8dbb68fae3b9806ab85af26398ea5/apps/web/src/lib/tools/locallibrary/oauth-client-metadata.json#L10)). The client isn't merged yet, so no Rust code on main reads flags.

Next to the platforms, this design is a small version of their split between client and server SDKs. It resembles OpenFeature's static-context client, which fetches a bulk evaluation once and evaluates from a cache ([OFREP README](https://github.com/open-feature/protocol)), except that public gates go to the client as rules and only the private part is resolved on the server. The one-hour refresh matches LaunchDarkly's mobile SDKs, which poll hourly in the background ([LD client vs server](https://launchdarkly.com/docs/sdk/concepts/client-side-server-side)). The 14-day last-known-good copy is what GO Feature Flag's `persistentFlagConfigurationFile` and Flagsmith's offline file handler do ([GOFF relay proxy](https://gofeatureflag.org/docs/relay-proxy/configure-relay-proxy); [Flagsmith server SDKs](https://docs.flagsmith.com/clients/server-side)). The client could borrow ETag and `If-None-Match` on the bulk answer from OFREP, so an unchanged hourly check costs a 304 ([OFREP openapi.yaml](https://raw.githubusercontent.com/open-feature/protocol/main/service/openapi.yaml)), though at current traffic it isn't worth adding.

OpenFeature itself sounds like the biggest gap and matters least. Every platform here ships OpenFeature providers, and Flipt, GO Feature Flag and the ConfigCat Proxy also speak OFREP ([OpenFeature ecosystem](https://openfeature.dev/ecosystem); [ConfigCat Proxy](https://configcat.com/docs/advanced/proxy/proxy-overview/)). The spec is still pre-1.0 at v0.9.0 ([spec releases](https://github.com/open-feature/spec/releases)), and what it buys is swapping vendors without rewriting call sites. Local Network has two consumers, both in this repo, locked to one rule by shared vectors. If a third consumer or a move to a hosted vendor ever comes up, `getFlags` is close enough to OFREP's bulk endpoint that an adapter would be a small job.

## Governance and environments

Governance is where the platforms put their price tags, and it's where Local Network looks best. Every flag change is audited as `flag.update` with field-level before and after values for `everyone`, `percentage`, `groups` and `accounts`, now joined by `enabled`, and a save with no changes writes nothing ([audit/log.ts](https://github.com/cutenode/localnetwork/blob/2f9d6c93a3b8dbb68fae3b9806ab85af26398ea5/apps/web/src/lib/server/audit/log.ts#L66-L90); [services/flags.ts](https://github.com/cutenode/localnetwork/blob/2f9d6c93a3b8dbb68fae3b9806ab85af26398ea5/apps/web/src/lib/server/services/flags.ts#L201-L234)). The log is hash-chained, copied to the network and checked by the syncer, and denied attempts are recorded too ([apps/web/README.md](https://github.com/cutenode/localnetwork/blob/2f9d6c93a3b8dbb68fae3b9806ab85af26398ea5/apps/web/README.md#L196)). LaunchDarkly lists its audit log and custom roles as Enterprise only ([LD pricing](https://launchdarkly.com/pricing/)), ConfigCat's free plan keeps 7 days of audit history ([ConfigCat pricing](https://configcat.com/pricing/)), and Flagsmith puts audit logs and roles at Scale-Up ([Flagsmith pricing](https://www.flagsmith.com/pricing#compare-features)). Access control is similar. Two grants, `flags` and `flagGroups`, are checked in page loads and again in the service, and admins hold both while moderators hold only what an admin gave them ([types.ts](https://github.com/cutenode/localnetwork/blob/2f9d6c93a3b8dbb68fae3b9806ab85af26398ea5/apps/web/src/lib/types.ts#L355-L356); [services/flags.ts](https://github.com/cutenode/localnetwork/blob/2f9d6c93a3b8dbb68fae3b9806ab85af26398ea5/apps/web/src/lib/server/services/flags.ts#L190-L192)). Unleash's open-source edition has no granular RBAC at all ([Unleash pricing](https://www.getunleash.io/pricing)). Change approvals, which every vendor sells as a paid feature (LD Foundation and up, Statsig Pro, Unleash Enterprise, GrowthBook Enterprise, PostHog by entitlement), would just add a step for a project with one maintainer ([LD approvals](https://launchdarkly.com/docs/home/releases/approvals); [Statsig pricing](https://statsig.com/pricing); [Unleash change requests](https://docs.getunleash.io/concepts/change-requests); [PostHog approvals](https://posthog.com/docs/settings/approvals)).

Environments are implicit, and that's enough. Each deployment reads the staff space of whichever root account `ROOT_IDENTIFIER` names ([config.ts](https://github.com/cutenode/localnetwork/blob/2f9d6c93a3b8dbb68fae3b9806ab85af26398ea5/apps/web/src/lib/server/config.ts#L66)), so a staging deployment with its own root has its own flag state. Platforms make environments first-class with separate keys, and the free tiers cap them at 2 or 3 (LaunchDarkly Developer 3, ConfigCat Free 2, Unleash open source 2) ([LD pricing](https://launchdarkly.com/pricing/); [ConfigCat pricing](https://configcat.com/pricing/); [Unleash pricing](https://www.getunleash.io/pricing)). This holds only as long as every non-production deployment uses its own root.

### The kill switch

At `2f9d6c9` there was no dedicated off control. Killing a flag meant opening its form, clearing "On for everyone", setting the percentage to 0 and removing every group and account, which saved a record that no longer said who the flag was for ([staff/flag.json](https://github.com/cutenode/localnetwork/blob/2f9d6c93a3b8dbb68fae3b9806ab85af26398ea5/lexicons/computer/localnetwork/staff/flag.json#L6-L35)). The audit log kept the old lists, but rebuilding a 200-account rollout from audit entries after a bug is the wrong kind of work. Every platform separates "off" from targeting. LaunchDarkly serves an off variation and leaves rules in place ([LD evaluation rules](https://launchdarkly.com/docs/sdk/concepts/flag-evaluation-rules)), FME's kill "serves the default treatment to everyone" over targeting ([FME targeting](https://developer.harness.io/feature-management-experimentation/use-fme/feature-management/setup/define-feature-flag-treatments-and-targeting)), flagd has `state: DISABLED` and GO Feature Flag has `disable` ([flagd definitions](https://flagd.dev/reference/flag-definitions/); [GOFF internal_flag.go](https://github.com/thomaspoignant/go-feature-flag/blob/v1.58.1/modules/core/flag/internal_flag.go#L26-L57)).

Local Network now does the same. `computer.localnetwork.staff.flag` has an optional `enabled` boolean, and a missing one means true. When it's false the flag is off for everyone, and its groups, accounts and percentage stay stored. The rule is now:

```text
on = enabled && (everyone || targeted || (did is known && bucket(key, did) < percentage))
```

`getFlags` returns `enabled` for each flag, and cases in `flags/vectors.json` cover it, as an optional field per case where missing means true. The flag's form in the staff console has an "Off for everyone" switch above the targeting, which stays visible and editable, dimmed, while the flag is off. Turning a flag off or on is audited under `flag.update` with an `enabled` field.

How fast a kill lands follows from the delivery numbers above: on the next request for the instance that wrote it, and within 60 s for other instances and for the public `getFlags` cache. ADR 0006's design for locallibrary caches for an hour and keeps the last answer up to 14 days offline, so an online computer sees the kill within the hour and one that stays offline can keep the old answer for up to 14 days.

### Hygiene and removal

Fowler calls toggles "inventory which comes with a carrying cost" and recommends expiry dates, a removal task created alongside each release flag, and time bombs that fail tests after expiry ([Fowler](https://martinfowler.com/articles/feature-toggles.html)). The platforms automate that judgement. Unleash gives each flag type an expected lifetime (release and experiment 40 days, operational 7, kill switch and permission permanent) and marks flags "potentially stale" once they pass it ([Unleash flags](https://docs.getunleash.io/reference/feature-toggles)). LaunchDarkly tracks statuses and a "ready to archive" stage that needs no code references ([LD flag status](https://launchdarkly.com/docs/home/flags/flag-status)). PostHog calls a flag stale when it hasn't been evaluated in 30 days or has been 100% rolled out for 30 days with no filters ([PostHog stale flags](https://posthog.com/docs/feature-flags/cleaning-up-stale-flags)). ConfigCat sends a zombie-flag report and scans code for references ([ConfigCat zombie flags](https://configcat.com/docs/zombie-flags/)).

Local Network had the hard half from the start. Deleting a catalog file breaks the build wherever the key is still read, which beats a code-reference scanner at the moment of removal ([flags/README.md](https://github.com/cutenode/localnetwork/blob/2f9d6c93a3b8dbb68fae3b9806ab85af26398ea5/flags/README.md#L3-L5)). What it lacked was anything that says when to remove a flag, since the only age signal was `updatedAt` in the admin list ([services/flags.ts](https://github.com/cutenode/localnetwork/blob/2f9d6c93a3b8dbb68fae3b9806ab85af26398ea5/apps/web/src/lib/server/services/flags.ts#L147-L165)). It now has two signals, following Fowler's time bombs and Unleash's lifetimes by type.

Each `flags/catalog/<key>.json` has a `type`: `release`, `experiment`, `ops` or `permission`. Release and experiment flags must have a `removeBy` date (YYYY-MM-DD), and the other types can't have one. A unit test fails once a flag is past its `removeBy`, naming the flag. `parityCanary` is `ops`.

The `/admin/flags` list marks a flag "Ready to remove" when it's enabled and either on for everyone or at 100%, and its record's `updatedAt` is 30 or more days old. That's PostHog's definition, worked out from fields already stored. Any saved change resets `updatedAt`, so editing a fully rolled-out flag starts its 30 days again.

Evaluation counts, the signal Unleash and LaunchDarkly lean on, would be useless here: the server hook evaluates every catalog flag on every request ([hooks.server.ts](https://github.com/cutenode/localnetwork/blob/2f9d6c93a3b8dbb68fae3b9806ab85af26398ea5/apps/web/src/hooks.server.ts#L103)), so every flag would always look in use. Exposure events and experiments, which LaunchDarkly, Statsig, FME, PostHog and GrowthBook build on top of evaluation logs ([PostHog exposures](https://posthog.com/docs/experiments/exposures); [GrowthBook results](https://docs.growthbook.io/app/experiment-results)), have no use here without an analytics pipeline, and the glossary's rollout-only scope rules them out anyway.

### Tests and overrides

The test suite is better than most platforms' guidance asks for. There are shared vectors, fast-check properties, service and route tests, a projection test that ignores records from non-root DIDs, an integration run on a real PDS, and a Playwright test where an admin targets one account and only that account sees the flag on. PR #456 also reports breaking the hash input, `<` vs `<=`, the signed-out check and the grant checks each once to watch a test fail ([evaluate.test.ts](https://github.com/cutenode/localnetwork/blob/2f9d6c93a3b8dbb68fae3b9806ab85af26398ea5/apps/web/src/lib/server/flags/evaluate.test.ts#L1-L60); [app.e2e.ts](https://github.com/cutenode/localnetwork/blob/2f9d6c93a3b8dbb68fae3b9806ab85af26398ea5/apps/web/tests/e2e/app.e2e.ts#L548-L588); [PR #456](https://github.com/cutenode/localnetwork/pull/456)). Tests set flags by calling `updateFlag` or passing `flags` into a route load, the same idea as OpenFeature's in-memory test provider ([spec appendix A](https://raw.githubusercontent.com/open-feature/spec/main/specification/appendix-a-included-utilities.md)). Pages rendered on their own read every flag as off, which covers Fowler's "fallback with new toggles off" case for free ([Fowler](https://martinfowler.com/articles/feature-toggles.html)).

Fowler also describes per-request overrides through a cookie, query parameter or header so testers can see a feature, and warns they can be tampered with unless signed ([Fowler](https://martinfowler.com/articles/feature-toggles.html)). GrowthBook supports forcing variations from the query string ([GrowthBook core.ts](https://github.com/growthbook/growthbook/blob/v5.2.0/packages/sdk-js/src/core.ts#L499-L691)). At `2f9d6c9` the only way to see a gated page in development was to sign in as an admin and target your own account through `/admin/flags`. There are two overrides now.

`FLAG_OVERRIDES=key=on,other=off` is read at startup, for development and tests. It applies to every request on that instance, `getFlags` included, so the website refuses to start if it's set with `NODE_ENV=production` or names a flag that isn't in the catalog.

Staff holding the `flags` grant can preview a flag from `/admin/flags/<key>`, turning it on or off for their own browser only. The preview is a signed, httpOnly cookie that expires after an hour. It's signed with the browser's session, so it stops working when they sign out or another account signs in, and it's only honoured while the viewer still holds the grant. A banner on every page says what's being previewed and has a Clear button. Each preview and clear is audited as `flag.preview`. A preview changes nothing for anyone else, and `getFlags` ignores it.

## Conclusion

The platforms' feature lists come from two pressures Local Network doesn't face: many teams editing flags at once (approvals, custom roles, environments, lifecycle dashboards) and flags used for experiments (variants, exposures, guarded rollouts, metrics). Without those, what's left is a hashing rule, a private targeting store, fast server evaluation and an audit trail, and Local Network has all four. Two of its choices go further than vendor products do: the build fails when a removed flag is still read, and every evaluator is locked to one rule by shared vectors. Those cover two failures the platforms charge for or document as pitfalls, flags that never get cleaned up and SDKs whose hashing drifts apart.

The operational gaps around the first real flag are closed: catalog-only changes run CI, a flag turns off without losing its targeting, developers and staff can see a gated feature without retargeting anyone, and the catalog and admin list say when a flag should go. What's left is the locallibrary client, whose preconditions (website deployed, one live sign-in, the production PDS accepting the staff collections) haven't been confirmed. The rest of what the vendors sell can be ignored.
